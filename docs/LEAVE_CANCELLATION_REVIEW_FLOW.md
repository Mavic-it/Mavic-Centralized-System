# Leave cancellation and rescheduling design

## Request detail clarity refinement

The existing RequestDrawer keeps its props and API contracts. Present a short status/next-step explanation before the summary, followed by the reason and current response/decision controls. Move full history to a collapsed native details disclosure below actions. Translate event codes to plain labels and remove internal request UUIDs from reschedule messages. Keep original audit data on the server. Use current drawer styling and single-column mobile behavior, native summary keyboard access and existing focus/error handling. Required comments depend on the selected action: approval may omit a comment; cancellation/rejection still require one. Files: request-drawer.tsx, a presentation helper and leave.module.css. Verify focused drawer tests, TypeScript and lint.

1. **Component tree:** existing Leave request form and request drawer; the drawer presents the current cancellation proposal and role-specific response/decision controls. Existing request tables and timeline remain.
2. **Responsibilities:** leave service owns all transitions, leave-credit/DTR updates, scope and ownership; controller validates DTOs; the drawer submits explicit decisions. A new cancellation-review table stores one open negotiation per request. Timeline events preserve previous attempts.
3. **Contracts:** an employee's pending request can still be withdrawn with a reason. An employee's future approved cancellation becomes a review request. An authorized reviewer may propose cancelling a pending/future approved request; the employee can confirm, explain why it should continue, or propose new dates. Confirming a reviewer proposal completes cancellation; declining preserves the leave. Proposed new dates go back to the reviewer; acceptance cancels the original and creates a new pending request for approval. Rejection preserves the original. Server checks scope and ownership on every call.
4. **State model:** `AWAITING_EMPLOYEE`, `AWAITING_REVIEW`, `CLOSED` / `REJECTED` review states. Only one open review per request. Original leave status and credits stay unchanged while review is open. Atomic final transition handles restoration, reservation and DTR sync. Existing loading/error/empty states remain; destructive decisions require the existing confirmation UI.
5. **Visual system:** a compact review panel inside the existing request drawer, status/callout, radio-like native select and dates only for rescheduling. Current action footer stays visible. Mobile drawer remains one column.
6. **Accessibility:** labeled native fields, required reason/dates, real buttons, visible focus, error alert, polite pending status. Keyboard flow and Escape remain managed by the existing modal.
7. **File plan:** migration for review state and reschedule link; leave DTO/controller/service/types/policy for server behavior; request drawer, request form and web types for actions and filing guidance; focused tests and tracker.
8. **Verification:** authorization/state/concurrency tests, credit and DTR transition tests, DTO rejection, focused UI and form tests, API build, frontend TypeScript, lint. No existing requests or credits are rewritten by migration.

Assumption: “2–3 days” means **3 calendar days** for new Vacation Leave (`VL`) and Leave Without Pay (`LWOP`) filings, in Philippine Time. Sick and Emergency leave retain their configured notice. Existing longer policy notices still win. This is enforced by the API and reflected in the form. Rescheduled dates must satisfy the same current filing and eligibility checks.

Accepted reschedule behavior: the employee does not directly change approved or pending dates. After employee response, an authorized reviewer approves or declines the date proposal. Approval transactionally cancels the original request (restores used credits where required), validates and creates a new PENDING request with recalculated workdays and reservation, preserves the original assigned approver when available, and copies supporting documents only when the new policy permits them. A new approval is still required.

## 2. Current architecture and relationships

- Monorepo applications: `application/api` is NestJS 12 with TypeScript; `application/web` is Next.js 16 App Router with React 19. Shared project files and documentation live at the repository root.
- PostgreSQL access is through TypeORM's `DataSource` with parameterized SQL in services. Schema changes are TypeORM migrations under `application/api/src/database/migrations`. Database synchronization and migration auto-run default to false; the API package exposes build, lint, unit-test, and e2e-test scripts.
- Authentication populates a typed request user (user ID, email, role, active branch). Authorization combines role/permission decorators and explicit controller checks. Scoped HR Admin and Branch Manager sessions select one active branch at a time from the account's primary branch plus active branches where it is the named manager. Session validation checks the saved session token and current branch membership on each request; switching issues a replacement session for the selected branch. Existing branch-scoped controllers continue to use the active branch. Branch scoping must be enforced server-side; frontend navigation is not an authorization boundary.
- `employees.id` is the stable internal key. `employee_number` is a separate generated human-readable identifier. `employees.branch_id` references `branches.id`; `users.employee_id` links a user to at most one employee through a partial unique index. `SUPER_ADMIN` has no branch and is unlinked by default; an explicit employee link remains supported for Super Admins who are also employees. `user_profiles` stores personal profile data for unlinked Super Admin accounts, keyed by `users.id`, and never creates or updates an `employees` row. Profile pictures are stored with that profile and are served only through an authenticated self endpoint.
- `branches.manager_user_id` links each branch's displayed manager to a user account with the `HR_ADMIN` or `BRANCH_MANAGER` role; its FK and nonunique index allow one account to be the named manager of several branches. `users.branch_id` remains the account's configured primary branch. Assigning a previously unscoped Branch Manager account sets that primary branch, writes an account-scope audit event, and revokes existing sessions. Changing a branch's named manager revokes the affected accounts' sessions; subsequent requests also recheck live membership so removed or inactive branch access is denied. Legacy `branches.manager_name` values remain available until replaced by a linked account. Separately, `employees` contains current assignment fields, employment and emergency-contact JSON, sensitive fields, and the current supervisor name plus `manager_employee_id`. `department_id` links to the branch-owned `departments` catalog; `position_id` links to the global `employee_positions` catalog. Compatibility text fields remain. `employee_profiles` stores extended personal and HR data. `employee_assignment_history` retains current and prior assignment snapshots with supervisor IDs and copied labels; old records whose effective dates were not reliably recoverable are explicitly marked unknown. `employee_work_schedule_history` stores effective-dated schedule snapshots; `employee_document_requirements` stores branch policy, and `employee_documents.requirement_id` connects uploads to checklist items.
- Attendance records reference employee and branch and retain schedule snapshots. Imported records now keep versioned DTR calculation/source/override JSON in the canonical table; retained clock records keep their existing path. Source batches/rows, templates/aliases, policies/holidays, period states, audit entries and export snapshots use additive related tables. Pre-retirement source data remains deleted; the restored schema does not recover it.

## 3. Gaps, inconsistencies, and dependencies

1. Before the active Phase 1 change, current employee fields were overwritten on change, losing transfer, promotion, status, and manager history.
2. Before the active Phase 1 change, `manager` was accepted by employee inputs but omitted from SQL persistence.
3. Employee assignment now has normalized department and position references, but legacy text remains and historical department values that do not match a branch catalog remain unlinked. Position catalog maintenance and a later legacy-column retirement need a staged compatibility plan.
4. Employee creation and extended-profile seeding are separate transactions, so a profile-audit failure can leave an employee without a seeded HR profile. Account creation/link checks and employee identity updates now use transaction locks; other lifecycle/account-state decisions remain for later work.
5. Employee update audit coverage now records changed field names without copying private values. Delete and broader lifecycle events still need consistent audit coverage.
6. Attendance supports retained schedules/clock/leave/correction workflows and the newly requested branch-aware DTR import/review/persistence/export slice. Exceptions require reconciliation; grace, breaks, OT and holidays require HR-approved configuration. Full payroll and broader attendance/leave reconciliation remain outside this request.
7. Reporting currently has an in-memory implementation and cannot be used as persisted HR analytics.
8. Sensitive salary, government ID, contact, and document data require explicit role and branch scope at every new API.

## 4. Proposed connected architecture

- Keep one canonical `employees.id` across all HR modules. Keep employee registration independent from account creation, with `users.employee_id` as the optional account link and the existing `SUPER_ADMIN` exception.
- Use the branch-owned department and normalized position identifiers introduced in Phase 1 for current assignments. Preserve human-readable assignment labels in append-only employee history so renames/transfers do not rewrite prior events.
- Write current employee changes, assignment-history events, and corresponding audit entries within one transaction. Keep salary history separate and restricted to authorized HR roles.
- Build shared approval, notification, audit, and lifecycle services only as needed by concrete workflows. Each module reads the canonical employee identity and applies branch/employee scope in its API service/controller.
- Keep API responses compatible during schema transitions; backfill existing records before switching reads/writes, and do not drop legacy columns until separately planned and approved.
- Resolve supervisors through the canonical employee record. Keep the old supervisor name as a compatibility label while backfilling only unambiguous matches; reject new unlinked supervisor names.
- Copy the configured branch schedule into the employee's effective-dated schedule history at creation, allow an explicit employee schedule, and make attendance use the employee's effective schedule. Keep the original branch schedule as the default for existing employees until an employee snapshot is assigned.
- Let HR define branch-specific required 201-file items without seeding unverified legal policy. Track the latest active, unexpired file per requirement and allow existing employee files to be linked to a requirement.

## 7. RBAC and branch-scope requirements

- `SUPER_ADMIN`: company-wide employee and HR access, with no branch/employee binding of its own.
- Company-scoped `HR_ADMIN`: company-wide HR administration with no branch switcher. Branch-scoped `HR_ADMIN`: its primary branch and active branches where it is named manager, one active workspace branch at a time.
- `BRANCH_MANAGER`: its primary branch and active branches where it is named manager, one active workspace branch at a time; only manager workflows appropriate to that role, and salary remains hidden.
- `IT_ADMIN`: account/system functions and minimized employee fields; no salary, private contact, government ID, leave, attendance, or document data through employee endpoints.
- `EMPLOYEE`/`STAFF`: own employee record and explicitly permitted self-service fields only.
- Every new history/read/write endpoint must authorize against the employee's current branch or own employee identity. Historical data must not become a branch-scope bypass after transfer. Salary history is excluded from the general assignment-history endpoint.
- Employee/account identity synchronization must remain inside the employee update transaction; account creation locks the employee while validating its email and linked-account status.
- Manager choices require an active `HR_ADMIN` or `BRANCH_MANAGER` account linked to an employee; assigning the same account to another branch is allowed. Changing an assigned account to another role requires removal from every named branch first. The active-branch switch endpoint accepts only a currently authorized active branch, replaces the issued session token, and all subsequent requests verify that the account still owns that branch. Company-wide HR and Super Admin retain their existing authorized scope.

## 9. Risks and compatibility

- Existing employee fields and JSON must remain readable while additive columns/history are introduced.
- Existing department strings may not match branch catalog entries exactly; matched values are linked and unmatched values remain readable through the compatibility text field until cleaned up.
- History visibility after a transfer must use a clearly defined policy; the current plan scopes reads by the employee's current branch, with self access retained.
- Backfilled history can recover only the current assignment. It cannot recreate undocumented past transfers; legacy effective dates are marked unknown rather than inferred.
- Sensitive data must not be copied into general audit details or broad history responses.
- Migration execution is disabled by default and must be handled by the normal deployment operator workflow.
- Removing the unique manager index allows several branches to reference one account. The rollback cannot safely restore uniqueness while duplicate assignments exist; those assignments must be resolved before rolling back. An account's primary branch continues to grant workspace access separately from named-manager assignments. Revoking a named assignment must invalidate stale sessions and deny subsequent requests to that branch.

- Weekly employee rosters require an existing branch or employee base schedule to provide time zone, break, and grace-period settings. Branch default shift times and location fill the roster; daily shift/location and work/rest values override them only when changed.

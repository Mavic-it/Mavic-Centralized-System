# Incident workflow extension - 2026-10-29

This user-authorized extension implements the attached complete-workflow requirements within the existing /incidents and /api/work/incidents module. Main HRIS Phase 1 remains active.

## Audit and contract

Existing: Next.js cards/table and detail drawer, Nest strict DTOs, branch/identity authorization, employee/management report creation, server audiences, append-only history/files, optimistic versions and idempotent submission. Gaps: clarification cannot be addressed directly to an admin-report subject; report and disciplinary statuses are coupled; acknowledgement, HR referral, resolution before closure, durable incident email, structured source/time/remarks, queue summaries/date filters and personal navigation are missing.

Preserve SUBMITTED (display Pending review) and DETAILS_REQUESTED (display Needs clarification) for compatibility. Add ESCALATED/RESOLVED; migrate legacy disciplinary report statuses into a separate nullable case_status on the same incident. Origin link is the incident id; no duplicate incident or case system. Legacy closed reports stay closed. History/evidence is never rewritten. Initial self-report identity is server derived; existing employee general reports remain supported. No automatic discipline, penalty, payroll effect or legal deadline.

Super/HR admins review within selected scope; Branch Managers still require explicit reviewer assignment. Only Super/HR may initiate formal discipline, resolve or close reports; assigned managers may acknowledge, clarify, note and refer to an authorized HR/Super reviewer. No self-review. Employees see only their canonical participation and authorized audiences. Internal notes never appear in employee payloads or message previews. Administrative reports remain immediately visible to their concerned employee.

Reuse existing drawer/tabs, files, forms, red/neutral CSS and sidebar groups. Report queue and discipline queue are tabs on the same page, with status shortcuts. My Incidents uses the same authorized module, not another data store. Summary counts are server totals, not page counts. Search/date/status filters are server-side for incidents.

## Implemented API and storage

No duplicate module or create endpoint. Existing GET /work/incidents now accepts search/from/to/queue (reports, active-cases, case-history), supports status=finished and returns authorized total/pending/clarification/resolved counts. Existing detail includes referenceNumber, reportSource, incidentTime, remarks, createdAt/updatedAt, reviewerName, caseStatus, resolvedAt/resolvedByName/resolutionSummary and closedAt. POST /work/incidents/report accepts optional incidentTime/remarks/reportMode; the employee form sends reportMode=SELF and the server derives the linked employee. Legacy GENERAL submissions remain supported through the existing contract. Unknown/forged status/source fields are rejected. Incident references are INC- plus the full UUID, generated by PostgreSQL with a unique constraint.

Existing POST /work/incidents/:id/actions adds RECEIVE (acknowledge), CLARIFY, EXPLAIN, HR_ESCALATE (requires authorized HR/Super reviewer id) and RESOLVE. COMMENT remains an audience-controlled follow-up/internal note. CLOSE now requires RESOLVED. Existing ESCALATE wire action means initiate a formal case and is restricted to HR/Super; HR_ESCALATE is the separate operational referral. Formal NOTICE/ACKNOWLEDGE/RESPONSE/DECIDE use case_status, not the report status. Every change locks the record, checks version, records report and case transition metadata and appends audit/history/notifications in one transaction. There is one linked formal case per report; no reopening or automatic penalties.

| Report state | Available transitions |
| --- | --- |
| SUBMITTED (Pending review) | acknowledge/review, request clarification, HR referral; addressed employee may explain |
| UNDER_REVIEW | request clarification, HR referral, HR resolution; explicit HR formal-case initiation |
| DETAILS_REQUESTED (Needs clarification) | addressed reporter/employee reply to UNDER_REVIEW, review or HR referral |
| ESCALATED | HR review, clarification or resolution |
| RESOLVED | HR closure only |
| CLOSED | read-only |

Acknowledge records an employee-visible response without resolving the report. Clarification exchanges remain in the same report and return it to UNDER_REVIEW. HR referral reasons remain INTERNAL with a separate generic visible referral event. Resolving a report with an unfinished formal case is rejected. Formal proceedings preserve the existing notice, non-admission receipt, explanation and decision prerequisites; a closed formal case leaves its report available for separate resolution/closure. Existing closed reports stay read-only.

Migration 1793318400000-IncidentWorkflow adds structured report fields, generated references, independent case state, resolution/closure metadata, indexes and work_mail_outbox. It maps only legacy mixed disciplinary states to UNDER_REVIEW plus case_status; original event history and private file bytes/audiences remain unchanged. Existing CLOSED formal records retain CLOSED in both dimensions. Deploy this forward migration before the updated API and UI as one coordinated release; the old mixed-state UI cannot represent independent case state. Recovery uses forward migrations/application compatibility; down intentionally refuses to discard personnel history.

## Notifications and operational delivery

Every relevant report/employee response event creates generic in-app notifications with incident reference, category, status, timestamp and authorized link. Internal notes produce no employee notifications. New notification rows enqueue incident email jobs inside the same business transaction. WorkMailService polls committed outbox rows every 30 seconds, claims jobs with FOR UPDATE SKIP LOCKED, rechecks active role/ownership and branch access and calls the existing EmailService/Nodemailer template. SMTP errors cannot roll back a report. Jobs retry with exponential delays capped at one hour for at most eight attempts; delivery/failure/attempt metadata is persisted. Configure the existing SMTP settings; after correcting configuration, an authorized operator may requeue failed unsent jobs through a reviewed operational update. No new external email provider or credentials were added. Delivery is at least once across an SMTP-success/process-crash boundary; no exactly-once provider guarantee is claimed. No narratives, evidence or internal notes go in email bodies or previews.

## Employee incident and discipline history (2026-10-30)

The employee 201 file and linked My Profile have an Incident / discipline history section. It requests the existing paginated incident endpoint with `employeeId`; the filter intersects existing record visibility and does not grant new access. It shows report reference, date, category, report/case status and offense classification, with a link to the private incident workspace. Employees cannot edit classifications. IT and independent account profiles do not receive a personnel history panel.

`POST /work/incidents/:id/offense` accepts the current version, `offense` (`AUTO`, `1`, `2`, `3`, `NONE`) and a required reason. An authorized different Super Admin, HR Admin or Branch Manager may classify records they already access as reviewer, reporting manager or reporter, within both original and current branch scope. Branch managers do not gain other case-review actions. This explicitly permits a management reporter to classify their own report concerning another employee, while preserving existing workflow self-review restrictions. Permissions and current employee branch are rechecked under lock.

Automatic numbering is opt-in on Save, using the highest latest recorded classification on other incidents for the same employee/category plus one, across all dates and branches. There is no annual reset or legal penalty inference. The first classification is 1st; after 3rd automatic numbering stops and asks for an explicit policy choice. Manual overrides and clearing require reasons. Existing reports start unclassified. No inference of misconduct is made from report submission or case status.

Persistence uses append-only `OFFENSE_RECORDED` SUBJECT work events plus the existing audit log, with employee/category snapshots and case version increments. Latest classification applies only to the current concerned employee; retagging does not transfer a previous employee's classification. Corrections retain previous events. The existing narrative/evidence audience rules remain. A per-employee/category advisory transaction lock serializes concurrent classification and stale case versions reject duplicate saves. There is no schema migration or retrospective data rewrite.

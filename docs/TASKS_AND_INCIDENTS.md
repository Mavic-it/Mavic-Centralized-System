## Contract and assumptions

**Tasks** (`/tasks`): Super Admin, HR Admin and Branch Manager assign work to 1-50 active employees in authorized active branches, including title, description, priority and due date. The employee identity is the existing `employees.id`; no duplicate person/account is created. Assigned employees can start work, report progress, comment and submit completion. A different authorized manager accepts completion or requests changes. Managers may cancel with a reason. A different authorized manager can replace the full assignee set on an open task; the actor must have authority over the original task branch and every current and new assignee branch. The task status, progress, due date and append-only history remain intact. Linked active accounts for new assignees receive an in-app update; eligible email accounts also receive assignment email. Removed employees lose task access. Completed/cancelled tasks are read-only and cannot be reassigned or reopened.

**Incidents & Discipline** (`/incidents`): operational users may report a concern within their authorized branch. Employees can submit a general workplace report or self-report; they cannot enumerate coworkers through the reporting form. Authorized reviewers can identify a concerned employee during fact finding, request details, resolve the report with a documented reason, or start disciplinary review. A disciplinary case requires a concerned employee. Reviewers issue a notice containing the allegation and company-approved response instructions; the employee acknowledges receipt (not an admission) and submits an explanation. The reviewer records findings and a decision and closes the case. There is no automatic finding of guilt, sanction, attendance alteration, payroll deduction or statutory-deadline calculation.

User-confirmed reviewer policy: Super Admin/HR Admin within authorized scope; Branch Managers only for reports/cases explicitly assigned to their account. Only Super/HR admins may designate/reassign a reviewer, and the target must currently hold access to the report branch. Reporters and concerned employees cannot investigate or decide their own case, including when they hold management roles. Another qualified Super/HR admin must handle that conflict. Closed cases are read-only; no automatic escalation or deadline expiry exists in this version.

## Task automation and branch reporting (2026-11-05)

The current task workflow supports daily, weekly and monthly recurring series with a required end date within one year, two shared starter templates, branch-specific custom templates, and server-generated Excel/PDF reports. Task search and export use the same role/branch visibility, status, assignee and branch filters as the list. Recurring series store a branch and same-branch assignee snapshot, create the first task immediately, and transactionally generate future dated tasks with standard task audit and assignment notifications. Generation pauses with an audit event when the creator loses branch authority or an assignee becomes inactive or moves branches. ## Permissions and trust boundaries

- IT Admin remains excluded from confidential incident and case access. An IT Admin linked to an active employee may access and receive notifications for tasks explicitly assigned to that employee, but gains no manager or review privileges. Staff/Employee can see only assigned tasks, their submitted reports, management-created reports concerning them and notices addressed to their own canonical employee identity.
- The API derives actor/role/scope from the existing validated session, validates DTO allowlists and IDs, and uses parameterized SQL. UI controls do not grant permissions.
- Management access requires both the record's original branch and the concerned employee's current branch to be in selected scope. A transfer cannot expose case history to a manager who lacks one of those branches. Own employee/report access remains available independently of the current management selection.
- Management mutations lock the work record and concerned employee row, check the expected version, and save state, immutable event, audit metadata and private notifications in one transaction. Stale updates return 409. Submissions use a client UUID with an actor check and transactional advisory lock for safe retries.
- The shared header branch selector filters management collections. Create/report forms retain branch or employee assignment fields because these specify the new record's owner. No extra page-level branch filter is introduced.

## Privacy and evidence

Every incident event has an audience: **reviewers only**, **reviewers and reporter**, **reviewers and concerned employee**, or **record participants** (reporter, current concerned employee and authorized reviewers). The API applies these rules to history and attachments. For reports created by Super Admin, HR Admin or Branch Manager, the current concerned employee can immediately see the original title/description without waiting for a formal notice. Selecting an employee later also grants this access and notifies their linked active account. The immutable CREATED event's actorRole determines this rule, including for existing reports; promoting or demoting the reporter later does not change it. Confidential reports created by staff/employees retain notice-only subject access and redact the original narrative. Internal notes and reporter-only follow-ups remain restricted in both flows; concerned employees receive no reviewer permissions. Changing the concerned employee removes the previous subject's access unless they independently qualify as reporter/reviewer. Employee access derives from the account's canonical employee link, independently of its selected branch view. Reporters do not receive another employee's private explanation or disciplinary decision. They can track report status and receive a generic closure update. Case reviewers see the complete event history; audit records contain actor identity/role, record/event IDs, transitions and assignment metadata without copying narratives or file bytes.

Evidence supports PDF, PNG and JPEG signatures, up to 5 MB per file and 20 files per record. Files are stored privately as database bytes linked to append-only events; no public file URL is created. Downloads reauthorize both record and event audience, are audited, and use attachment disposition, no-store, nosniff and sandbox headers. The web proxy forwards the session, bounds request size, enforces same-origin writes and masks transport failures. Filename sanitization and signatures are validated server-side. Signature checks are not malware scanning; deployments needing antivirus/DLP must add an approved scanning service. This version does not introduce one or send evidence to an external provider.

The Create Task and Report an Incident forms accept one optional initial file. Forms with a file use multipart submission to the existing create endpoint; requests without a file retain the JSON contract. Record, attachment, history, audit and notifications commit together. Invalid files or attachment failures leave no partial record, and retries with the same submission key do not duplicate evidence. Initial task evidence is visible to authorized task participants; initial evidence on new management-created incidents is shared with the reporter, current concerned employee and authorized reviewers. Initial employee-report evidence remains reporter/reviewer-only. Existing evidence retains its immutable audience; this update does not retroactively release previously private attachments. More files can be added in the details drawer. No schema migration is required for initial uploads.

## Task delivery and management updates (2026-11-05)

Task assignment emails are queued for each linked active assignee account during task creation. A background outbox sweep queues one private reminder per assignee for each task due the next day in the Asia/Manila calendar. The reminder outbox is deduplicated by task, user and due date, and delivery rechecks that the account and employee are active, the task is still open, and the due date has not changed. Mail contains no task title, description, comments or evidence.

Managers can narrow the authorized task list by an assignee. Filter choices come from the manager's currently authorized branch scope, and the API applies the filter after its existing task visibility and branch-scope rules. A task creator can soft-delete their own task while they retain current manager authority over all branches and assignees on that task. Soft deletion hides it from active lists and access endpoints, but retains immutable events and an audit entry; other managers and assignees cannot delete it. Task detail files have an in-app PDF/image preview and retain their authorized download action. Inline responses are restricted to the existing PDF, PNG and JPEG allowlist and continue to reauthorize access on every request.

Authorized managers who are not current task assignees can replace all assignees on an open task from its detail view. The API locks the task and candidate employee rows, validates the expected version, active employee status and the manager's branch scope, then swaps the current assignment links in one transaction. Each replacement is recorded as an immutable `REASSIGNED` event and audit row with the prior and new employee IDs and their branches. Existing status and progress are retained. Current assignees and the task creator receive an in-app update; assignment email is queued only for newly added assignees, avoiding duplicate emails to retained assignees. A manager who is also an assignee cannot remove themself to bypass independent review.

The refreshed interface defaults to cards with a table option. Server status/team/personal filters and pagination retain the authorized dataset; search, sort and Active/Closed counts apply to the currently loaded page and are labeled accordingly. Details use Overview, Activity, Files and Update tabs, retaining draft form inputs when switching sections. The overview opens the relevant permitted action; saving still requires an explicit submission and existing confirmations. Files support drag/drop, native selection and removing an unsaved selection. Task progress offers a synchronized slider and numeric input. Design and verification: `docs/WORK_MODULES_UI_DESIGN.md`.

In-app notifications use the existing inbox and generic messages linking to an authorized record. No disciplinary narrative appears in public dashboards or notification bodies. Task SMTP email covers assignment, due-tomorrow reminders, review submission, changes requested, accepted completion and cancellation; routine comments, files and progress remain in-app only. Realtime invalidation uses the existing shared infrastructure.

## Storage and rollout

Additive migration **1793232000000-TasksAndIncidents** creates `work_tasks`, `workplace_incidents`, `work_events` and `work_attachments`, with canonical employee/user/branch foreign keys, status/progress/audience constraints, collection indexes, ordered append-only history and immutable evidence triggers. It reinstalls the standard realtime table triggers. Existing employee, attendance, leave and payroll records are preserved.

Forward-only migration **1794096000000-TaskReminderAndCreatorDeletion** adds soft-delete metadata for tasks, the task-mail outbox reminder date and an idempotency index for due-tomorrow reminders. Existing task records and mail history are preserved.

Forward-only migration **1794182400000-TaskAssigneeMailRecovery** requeues assignment emails previously suppressed for active IT Admin assignees, but only when their task remains open and assigned to them. Incident email policy and completed/cancelled tasks are unaffected.

Forward-only migration **1794268800000-TaskReassignment** replaces the immutable current-assignee guard with a transaction-scoped reassignment guard. Task events, audit records and evidence remain append-only; the current assignee rows are mutable only inside the authorized service transaction.

Follow-up migration **1793232001000-CompleteWorkHistory** safely adds ordered event IDs and metadata if an automatic development watcher registered the initial schema during implementation. It is a no-op for those columns on fresh installations and installs the normal realtime hooks. No original narrative or evidence is rewritten.

Deploy all task migrations before the new API/UI. Migration rollback intentionally refuses to drop task or confidential-case records; recover application compatibility by reverting application code while preserving the additive tables, or use an approved forward migration. No automatic disposal or historical rewrite is supported. Retention/export/disposal needs a separately approved company policy and audited workflow. Backups must protect the database and private evidence. Evidence contributes up to 100 MB per record, so normal database capacity and backup monitoring apply.

## Acceptance and validation

- Success paths: assign/reassign/start/progress/submit/change request/accept; report/review/follow-up/identify subject/designate reviewer/notice/acknowledgment/explanation/decision; evidence upload/download; in-app notifications and history.
- Failure paths: unauthorized roles, unrelated employee, unselected branch, transfer bypass, undesignated/conflicted reviewer, invalid dates/DTO fields/transitions, stale versions, unsupported/oversized files, wrong evidence audience and immutable-history changes. Audit failure must roll back the related status change.
- UI: loading/empty/error/retry states, status and personal/team views, contained table scrolling, accessible modal/confirmation controls and 320/640/1024/1440px layouts.
- Isolated PostgreSQL tests create a private fixture schema inside a transaction and roll it back. Browser fixtures use artificial accounts and intercepted API responses. These checks do not submit real tasks, reports, decisions, notifications or evidence to business tables.

## Report submission correction (2026-10-28)

The initial report path could fail with PostgreSQL `42P08` while creating reviewer notifications: the same branch parameter was inferred as `varchar` for the notification destination and `text` for access-grant array comparisons. The fix explicitly casts that selected branch parameter to text, preserving the existing recipients and the report/notification transaction. No migration or permission change is required. The isolated integration fixture now clones the real notification table structure instead of simplifying all columns to text, and a regression asserts successful report creation and reviewer notification together. A diagnostic against the configured real schema reproduced the error inside a transaction that was always rolled back; no diagnostic report or notification is committed.

Report submission verification: all 17 module tests, type-aware lint and the API production build passed. The corrected query also completed the configured-schema submission path in a rollback-only diagnostic; no diagnostic report or notification was committed.

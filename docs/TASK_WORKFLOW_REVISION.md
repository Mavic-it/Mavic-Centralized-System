# Task workflow revision - 2026-10-29

Email policy update (2026-10-29): task emails are limited to new assignment, submission for review (including Done), changes requested, accepted completion and cancellation. The actor is excluded; review mail targets the authorized creator, and other mail targets affected assignees. Routine comments, files, progress and Started/In progress/Stuck updates remain in-app only. Jobs are stored atomically in additive migration `1793318403000-TaskMailPolicy`, retried by the work mail worker, and suppressed if the recipient loses current access. Emails contain an action and secure workspace link, but no task description, comments or files. Existing in-app activity is retained. Focused work/email tests: 84 passed; API build and type-aware lint passed. No real SMTP was sent.

User-authorized extension of the existing task module; HRIS Phase 1 and incident workflows remain unchanged.

## Task automation and branch reporting (2026-11-05)

Manager task collections can be filtered by an authorized branch, assignee, status and search term. Excel and PDF exports use the same server-side visibility and filter contract as the task list, including selected branch scope; exports are capped at 5,000 tasks and ask the user to narrow larger reports. Spreadsheet text is protected from formula execution. PDF reports contain task summary fields and a bounded description excerpt.

Managers can start from shared office inspection / room preparation templates or save branch-specific task templates. Templates store title, description and priority only; assignees and schedule are chosen for each task. Template reads and writes require manager role and current branch authority. Names are case-insensitively unique within a branch.

Recurring tasks support daily, weekly and monthly schedules with a required finite end date no more than one year from the first start date. Creating a series creates its first task immediately. Future occurrences use the original start date as their cadence anchor (monthly dates retain their day where possible), the same branch and assignees, and the same spacing between start and due dates. An authorized manager can stop future occurrences on an active series; existing tasks remain individually manageable. The API worker generates due occurrences in the Asia/Manila calendar, transactionally with assignee rows, immutable task history, audit, in-app notifications and the existing assignment-mail outbox. A unique series/date index and row locks prevent duplicate occurrences across API instances. Recurrence is limited to one branch; if the creator loses branch authority or an assignee becomes inactive, changes branch, or the branch is disabled, the series pauses and records an audit event. The initial and generated tasks remain individually manageable under existing task rules.

Forward migration `1794355200000-TaskAutomation` adds shared and branch-scoped templates, recurring series and assignee snapshots, and links generated task occurrences. Deploy the migration before the updated API; `DB_MIGRATIONS_RUN` remains opt-in. Branch filters intersect the session's existing authorized branch scope and never expand it.

Repair migration `1794355201000-RepairTaskAutomationTemplateLink` adds the missing `work_tasks.template_id` column and foreign key on databases that recorded TaskAutomation before that link was present. It is safe on schemas that already have the column. Without it, task list and detail queries fail with PostgreSQL error `42703`. The configured local database applied the repair on 2026-11-05; the task list query succeeded afterward.

## Authorized reassignment follow-up (2026-11-05)

Managers who are not current task assignees can replace the complete assignment list of an open task with 1-50 active employees in their authorized branch scope. The server checks the original task branch, all current and new employee branches, task version and assignee independence inside one transaction. Status, progress, due date, comments and evidence remain unchanged. Removed assignees lose access immediately; new employees become participants and linked active accounts receive in-app updates, with assignment email sent to eligible accounts. The immutable `REASSIGNED` event and audit row retain prior/new employee IDs and branch IDs. Review, task cancellation and independent approval rules do not change; reassignment cannot reopen a closed task.

Forward-only migration `1794268800000-TaskReassignment` changes `work_task_assignees` from immutable assignment history to guarded current-state rows. Only the authorized reassignment transaction can update/delete those rows; append-only work events, audit records and evidence remain immutable. The existing task action endpoint accepts `REASSIGN` and a validated `employeeIds` list.

Contract: task details use one scrollable view with the brief, status/progress, inline comment/review/file composer, metadata and activity history visible together. Files appear once beside the update that added them, with unlinked legacy files retained in the same history area. No separate task Overview, Activity, Files or Update navigation is needed. New create form accepts a required start date and 1-50 active authorized assignees. One task, discussion, evidence and shared status are visible to all assignees, not duplicate independent tasks. Managers must have access to every original/current assignee branch; employee participation remains independent of management filters. A manager who is any assignee cannot approve the task. Every assignee is notified.

Status selection: Not started=0%, Started=10%, In progress=50%, Stuck=last progress with red color, Done=100% and FOR_REVIEW pending independent manager acceptance. Existing legacy START/PROGRESS/SUBMIT actions remain compatible. Dates are calendar dates; start cannot exceed due date. Existing tasks retain unknown start dates rather than inventing history. Existing single employeeId remains compatible; new employeeIds is bounded/unique/validated. The canonical primary employee remains the first assignee while a backfilled junction table owns all participation.

Optional comment/review attachment is persisted on the same immutable event in the same transaction as the action; invalid evidence, count limits, stale versions or audit errors leave no partial status/comment/file. Private file download authorization is unchanged. Initial multi-assignee create remains idempotent and atomic. Task reassignment is covered by the follow-up above; reopening, incident redesign and later-phase features remain outside scope.

Validation: status mapping and transition rules, multi-assignee read/write/notifications, mixed-branch/transfer restrictions, independent review, dates, strict multipart input, atomic action attachments and rollback; web tests/type/lint/build plus real-component mocked browser flows at mobile/tablet/desktop. No real task/evidence/notification is submitted by checks.

## Implementation and rollout

Migration 1793318401000-TaskCollaboration adds nullable start_date, STARTED/STUCK states and a canonical work_task_assignees junction with original branch snapshots. It backfills existing primary assignees without changing task IDs, descriptions, progress, dates, events or evidence. Assignment changes are retained in append-only task events/audit rows; the junction stores the current participant set. Down refuses to discard task data. The local watcher registered the migration and a read-only check confirmed it is applied. Deploy the migration before the updated API/UI elsewhere.

Existing POST /api/work/tasks/task accepts employeeIds (JSON array, or JSON-encoded array in multipart), optional legacy employeeId, and startDate. New UI requires startDate; legacy clients may omit it. All assignees must be active and in the creator's authorized branch scope. GET list/detail/download uses the complete assignment set and retains employee access after branch selection/transfer. Management read/write requires all original and current assignee branches. The primary employeeId remains compatible; assignees contains safe names, IDs and original branch labels.

Existing POST /api/work/tasks/:id/actions accepts JSON or multipart with one optional PDF/PNG/JPEG up to 5 MB. STATUS plus taskState derives progress server-side. COMMENT, STATUS/DONE, legacy SUBMIT and reviewer actions can attach a file to that exact immutable event. Version, scope, 20-file cap, evidence and audit checks execute atomically; invalid/stale requests do not partially save. All assignees receive private in-app notifications. Legacy numeric progress and existing history remain as recorded until a new status update.

Frontend files: task-overview.tsx contains the combined task details, activity timeline, file display and inline workflow; task-assignee-picker.tsx provides searchable selection, removable participant chips, add-visible/clear actions and the 50-person guard; task-status.ts centralizes presentation mappings; record-file.tsx shares the authorized download card; workspace.tsx handles shared transport/creation and keeps incident tabs intact. The task creation form groups assignees, schedule dates and four descriptive priority choices in responsive panels. Shared progress colors are neutral/blue/purple/red/green for Not started/Started/In progress/Stuck/Done. Adding a file alone uses the same inline composer and requires no comment text.

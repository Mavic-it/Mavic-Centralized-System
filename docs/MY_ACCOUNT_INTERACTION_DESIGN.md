# My Profile as a self-service 201 file

1. **Component tree:** My Portal retains the authorized page and own-employee query. Its profile hero, EmployeeFileFacts, and section navigation use the same presentation classes as Employee 201 file. The section body composes EmployeeHrProfileCard, EmployeeWorkScheduleCard, EmployeeDocumentsSection, EmployeeAssignmentHistoryCard, emergency contact facts, and the existing payslip state. Independent Super Admin My Profile remains its separate personal-account form.
2. **Responsibilities:** My Portal owns section selection and the linked employee identity. Each reused module owns its existing API query, loading/error/retry UI and its own allowed actions. The portal never chooses another employee ID.
3. **Contracts:** `section=profile|work-schedule|emergency-contact|documents|assignment-history|payslips` selects the visible panel. Unknown/forbidden sections fall back to profile. The Employee record comes from `/employees/me`; child components use its internal ID. Existing API and mutation contracts remain.
4. **State model:** the section lives in the URL, supporting direct links and back/forward; child query and editor state remains local. Existing portal loading, unlinked, error and independent-admin redirect states remain. The HR card may edit personal fields through its existing controls. Self-service photo upload and emergency-contact editing remain available in this page. Schedule and documents are read-only in self-service.
5. **Visual system:** retain the 201-file hierarchy: full-name hero and status, four employment fact tiles, horizontal section tabs, then one detailed panel. Responsive tabs scroll horizontally instead of compressing labels. Remove both Open/View 201 file links and the short four-field summary.
6. **Accessibility:** tab buttons remain keyboard operable with visible focus, `aria-pressed`/`aria-controls`; the visible region is labelled and announced. Photo and emergency controls use labelled inputs, pending/error feedback and a focus-managed modal; child components retain their form labels, errors, confirmations and reduced-motion behavior.
7. **File plan:** change `application/web/app/components/people-workspace.tsx`, `portal-presentation.tsx`, `page-loading.tsx` and the shared module CSS for self-service composition/loading, update `portal-presentation.spec.tsx` for all section and role states, and update the HRIS tracker.
8. **Verification:** focused portal/201-file tests, frontend TypeScript and ESLint, source check for obsolete links; inspect narrow responsive rules. No API/schema/permission changes.

The feature stays within active HRIS Phase 1 and uses the existing self-service authorization enforced by the API.
